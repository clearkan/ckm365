Built and shipped in 2.7.0. ONE entry point as the sketch asked: add_attachment picks direct contentBytes under 3 MB and an upload session over, up to Graph's 150 MB ceiling, and callers never choose. Size is taken with stat() not read_bytes(), so an oversized file is refused without being loaded - the old code read the whole file into memory and THEN rejected it. Chunks stream off the disk and are never base64'd. The pre-authenticated uploadUrl gets its own bounded retry and resyncs to nextExpectedRanges rather than trusting our byte counter; a chunk that keeps failing raises with its offset. CKM365_ATTACH_ROOT confines both paths (pinned by a test). Over the ceiling the error says whose limit it is, per the note about the "in Outlook I can add up to 50 MB" complaint. TWO CORRECTIONS TO THIS TICKET, both found while building it. (1) The sketch said chunks must be a multiple of 320 KiB AND that 4 MiB worked live; those contradict each other, because 4 MiB / 320 KiB = 12.8. An assert caught it. Resolved by using 12 x 320 KiB = 3.75 MiB, which satisfies the documented rule and sits just under the size already proven twice live. (2) Undocumented, and it cost a live round: the session answers its LAST chunk with a Location header in OData FUNCTION form - Attachments(...id...) with the id quoted and usually percent-encoded - not the attachments/{id} shape the rest of the API uses. Parsing it as a path segment gives 400 RequestBroker--ParseUri, which is exactly the error this ticket's own incidental finding warned about, arriving from a different direction. Both shapes are now parsed and four spellings are pinned by a test. VERIFIED LIVE ON BOTH TENANTS: a 5,255,225-byte random (incompressible) file attached through the session, listed, downloaded back and SHA-256 compared - bytes identical; reported size 201 bytes over the source, which is the MIME framing and matches the +210-230 B measured in CKM-32; draft discarded with a 404 confirming no residue. Offline 162 passed / 15 skipped, covering chunk sequencing, no-bearer-on-the-PUTs, resume via nextExpectedRanges, loud failure carrying the byte offset, the 3 MB boundary picking the direct path, and root confinement on the large path. The >150 MB refusal is tested with a SPARSE file, so it also fails loudly if anyone reintroduces a read before the size check. OUT OF SCOPE as the ticket said: calendar-event attachments, and any client-side compression or format conversion.
