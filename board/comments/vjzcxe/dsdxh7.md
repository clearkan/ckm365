Done in v2.3.0. get_message_headers(message_ids) — read tier, curated, batched 20 to a /$batch round trip in the same id-list/partial-failure shape as the CKM-33 triage tools but without the write gate; get_message carries the same projection for a single message. Curated subset exactly as specified (List-Unsubscribe, List-Id, Precedence, Auto-Submitted, X-Auto-Response-Suppress, Return-Path), never the raw bag, with is_bulk and is_auto_reply DERIVED alongside the raw values so the derivation is auditable. Values are sanitised (control characters become spaces — a header must not inject line breaks into a log or a context) and capped at 200 chars with a trailing ellipsis; live sampling showed only List-Unsubscribe ever exceeds that (mean ~330, max 543). The untrusted-input warning is in the tool docstring and the model docstring, both saying classification and prioritisation, never authorisation or trust. THE ISSUE'S SKETCH WAS WRONG ON ONE FACT: internetMessageHeaders IS returned on a collection GET when explicitly $selected — verified on both tenants, 25/25 rows populated, 47-86 headers each. So the N+1 hazard the issue was guarding against does not exist. The tool stays per-message and deliberate anyway, but on VOLUME grounds instead: those rows cost ~10.6-11 KB each, ~11x a summary row, which is the real reason list_messages must not carry them (a test asserts it never asks for them). Recorded in AGENTS.md gotchas so the next agent does not re-derive it. Return- Path is returned raw with no derived flag: a differing Return-Path is normal for VERP and ESP traffic, so a flag would have been noise — the caller compares it with the sender itself.
