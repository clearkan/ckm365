Done in v2.3.0. ROUTE: named fields, NOT a caller-supplied $select — recorded deliberately. Models own their $select here, so a caller-driven projection would make the return shape dynamic, push Graph's own field names into consumer code, and hand an agent a way to ask for exactly the fields these tools keep off list rows on purpose (bodies, header bags). Named fields are additive on the pinned API and the MCP schema stays self-describing. ONE CORRECTION to the sketch: the fields are `to`/`cc`, not `to_recipients`/ `cc_recipients` — Message already exposes `to`/`cc` for the same concept and inherits from MessageSummary, so the sketch's names would have given one object both. They moved to the base class instead; Message.to/.cc keep their names, so nothing downstream renames. bcc omitted from listings (Graph populates it only on the sender's own copy — an empty column on nearly every row); get_message still returns it. VOLUME MEASURED BEFORE DECIDING: +141 bytes/row, +17% (848->988 and 830->970 B/row over 100 real inbox rows on each tenant) — not enough for an opt-in flag, so list_messages has none; a caller paging thousands who disagrees gets a new issue. Live: 25/25 sentitems rows carried `to` (11 and 58 distinct correspondents from ONE call), and 25 inbox rows carried 12 and 15 DISTINCT delivered-to addresses with 21/25 and 20/25 addressed to something other than the primary address — so alias-based party resolution now has the signal it needed. No new consent (ordinary message properties under Mail.Read). Recipient-based server-side filtering and address-book resolution stayed out.
